# 🛍️ Store — E-Commerce Platform

_Современный, премиальный и высокотехнологичный интернет-магазин — портфолио-проект._

**Демо:** [store-mauve-nine.vercel.app](https://store-mauve-nine.vercel.app/)

**Store** — полноценное веб-приложение для электронной коммерции,
построенное на **Next.js 16** (App Router, Turbopack), **React 19**,
**TypeScript 5.9** и **Redux Toolkit 2.9**. Приложение обладает премиальным
дизайном в стиле **Glassmorphism**, лавандово-графитовой темой,
синхронизацией состояния каталога с URL, отзывчивой мобильной версией,
тактильным откликом (Haptics), отзывами на товары, уведомлениями в
реальном времени, полноценной админ-панелью для управления магазином и
глубокой интеграцией с **Supabase** для аутентификации, корзины,
избранного и истории заказов.

**Стек:** Next.js 16 (App Router, Turbopack) · React 19 · TypeScript 5.9 ·
Redux Toolkit 2.9 + RTK Query · redux-persist · Supabase (PostgreSQL + Auth
через `@supabase/ssr`) · SCSS Modules · React Hook Form + Zod

## 🏗️ Архитектура проекта (Feature-Sliced Design)

Проект спроектирован с использованием архитектурной методологии
**Feature-Sliced Design (FSD)** поверх Next.js App Router, что обеспечивает
строгую, предсказуемую и масштабируемую структуру с упором на строгое
разделение ответственности, модульность и соответствие соглашениям (BEM,
SCSS Modules).

```text
app/              # Next.js App Router: маршруты, layout'ы, гварды, Server Actions
src/
├── app/            # Настройка Store, провайдеры, глобальные стили (FSD-слой "app")
├── views/          # Композиции страниц (CatalogPage, ProductPage, страницы админки и др.)
├── widgets/        # Сложные самостоятельные UI-блоки из фич и сущностей (Header, CartDrawer)
├── features/       # Пользовательские взаимодействия и бизнес-действия (cart-actions, checkout-process)
├── entities/       # Бизнес-сущности и их отображение (Product, User, Order, Review, Notification)
└── shared/         # Переиспользуемая инфраструктура, UI-kit, конфиги, типы, утилиты и API
```

### Ключевые архитектурные решения

1. **Feature-Sliced Design (FSD)**: строгое следование принципам FSD,
   механически проверяется через ESLint (`no-restricted-imports`).
   - **Однонаправленные зависимости**: `views` -> `widgets` -> `features` -> `entities` -> `shared`. Модули могут импортировать только из нижележащих слоёв.
   - **Публичные API (Public API)**: каждый слайс экспортирует свой интерфейс через `index.ts` (Barrel-файл). Внутренние кросс-импорты между слайсами запрещены.
2. **Осознанная стратегия рендеринга для каждого маршрута**: `/` и
   `/product/[id]` генерируются статически с ISR (почасовая ревалидация,
   плюс ревалидация по требованию при мутациях); `/catalog` рендерится на
   сервере для первого экрана с фильтрацией на клиенте; `/user/*`,
   `/checkout/*`, `/admin/*` полностью клиентские и защищены гвардами.
   `proxy.ts` (middleware App Router) обновляет cookie сессии Supabase и
   перенаправляет неавторизованных пользователей на каждом запросе.
3. **URL как единственный источник правды (Single Source of Truth) для
   каталога**: параметры поиска (`?q=`), сортировка (`?sortBy=`) и
   категория (`?category=`) хранятся и управляются исключительно через URL
   (`useSearchParams`/`searchParams`). Это позволяет делиться ссылками,
   сохранять их в закладки, а также обеспечивает корректную работу кнопок
   «Назад»/«Вперёд» в браузере.
4. **Тонкие компоненты и вынесение логики в модели/хуки**: все UI-компоненты декларативны.
   Запросы к API, манипуляции с роутером, вычисление производных состояний и
   валидация происходят в специализированных сегментах слайсов (`model`, `lib`, `api`).
5. **Нормализация кэша в RTK Query**: ответы API трансформируются в
   структуру `{ ids: number[], items: Record<number, Product> }` для O(1) поиска
   и снижения нагрузки на рендеринг.
6. **Селективное кэширование в LocalStorage (Redux Persist)**: в локальное
   хранилище записываются только самые важные данные по каждому слайсу
   отдельно: `cart.items`, `wishlist.favoriteItems`,
   `checkout.items`/`draft` и `auth.user` (сама сессия Supabase хранится в
   httpOnly cookie, а не в localStorage). Кэш запросов RTK Query и
   временное состояние UI не персистируются.

## 💎 Главные фишки и особенности

- 🎨 **Премиальный дизайн в стиле Glassmorphism и лавандово-графитовая
  тема**: тщательно подобранная цветовая палитра, размытие заднего плана
  (backdrop-filter), мягкие тени и плавные микро-анимации на основе физики
  пружин.
- ⭐ **Отзывы на товары**: рейтинги, привязанные к подтверждённой истории
  покупок, гистограмма распределения оценок, сортируемые и фильтруемые
  списки отзывов с пагинацией, оптимистичные лайки и страница «Мои отзывы»
  с написанными и ожидающими (по неоценённым покупкам) отзывами.
- 🔔 **Уведомления в реальном времени**: центр уведомлений с бейджем
  непрочитанных, синхронизация в реальном времени через подписки Supabase
  и триггеры на смену статуса заказа, ответы на отзывы и снижение цены в
  избранном — отдельно от кратковременных toast-уведомлений о мгновенных
  действиях (добавление в корзину, изменение фильтров).
- 🧾 **Оформление заказа в виде вертикального аккордеона**: многошаговый
  процесс контакты → доставка → оплата с масками для телефона и почтового
  индекса, автосохранением черновика, подстановкой данных из последнего
  заказа и конфетти на странице успешного оформления.
- ⚡ **Оптимистичные обновления (Optimistic Updates)**: при изменении количества
  товаров в корзине или переключении избранного интерфейс реагирует мгновенно.
  Изменения отправляются на сервер в фоновом режиме, а в случае сбоя состояние
  автоматически откатывается (`patchResult.undo()`).
- 📳 **Тактильный отклик (Haptic Feedback)**: интеграция библиотеки
  `web-haptics` для приятной вибрации мобильного устройства при добавлении в
  корзину (`soft()`), изменении фильтров (`light()`) или успешном оформлении
  заказа (`success()`).
- 🔍 **SEO и Core Web Vitals**: серверный рендеринг/ISR для страниц товара и
  каталога, динамическая sitemap и генерация OG-изображений, `noindex` для
  приватных разделов (`/user`, `/checkout`, `/admin`).
- ⚙️ **Строгая методология BEM**: CSS-классы написаны строго по БEM
  (`block__element--modifier`), импортируются в JSX исключительно через
  типизированные SCSS Modules: `className={style['cart-item__btn--remove']}`.
- 🔄 **Двухэтапная синхронизация корзины и избранного**: авторизованные
  пользователи работают с облачной базой Supabase. При входе в аккаунт локальная
  корзина и избранное из `localStorage` объединяются с серверными
  (merge-on-login), предотвращая потерю выбранных товаров.

## 🔌 Бэкенд (Supabase)

Аутентификация, каталог товаров, корзина, избранное, отзывы, уведомления и
заказы работают на **Supabase/PostgreSQL** со сквозной **Row Level
Security**: каждый пользователь может читать/изменять только свои строки в
`cart_items`, `wishlist_items`, `product_reviews`, `notifications` и
`orders`. Оформление заказа проходит через единственную RPC-функцию
`create_order` (`SECURITY DEFINER`), которая проверяет вызывающего
пользователя, рассчитывает доставку и комиссию оплаты на сервере и вставляет
заказ вместе с позициями в одной транзакции — так что при сбое чекаут не
может оставить частично сохранённые данные. История статусов заказа
фиксируется и запускает уведомления в реальном времени; рейтинг товара
кэшируется и синхронизируется через триггеры.

## 🧪 Тестирование

**E2E-тесты на Playwright** (`pnpm test:e2e`) покрывают P0-сценарии
витрины — каталог/поиск, гостевую корзину, гварды авторизации и полный
чекаут с оформлением реального заказа — против боевого проекта Supabase, а
не мок-бэкенда. Нужны `SUPABASE_SERVICE_ROLE_KEY` и отдельный тестовый
аккаунт `E2E_USER_EMAIL` / `E2E_USER_PASSWORD` в `.env`; полный список
сценариев и то, как устроена очистка после прогона — в разделе "E2E Tests"
файла `AGENTS.md`.

## 🛠️ Админ-панель

Полноценная панель управления магазином доступна по адресу `/admin`,
защищена на сервере (в `admin/layout.tsx`) и хелпером `is_admin()` в RLS,
читающим колонку `role` в `profiles` (по умолчанию `'user'`) — без Auth
Hook в Supabase. Все административные записи проходят через RPC-функции
`SECURITY DEFINER`, которые сами проверяют `is_admin()`, а не через
политику RLS с проверкой роли — у `orders`/`order_items` намеренно нет ни
одной write-политики.

Она включает:

- **Дашборд**: счётчики заказов, выручки и покупателей, аналитические панели.
- **Заказы**: список, фильтр по статусу, поиск по номеру заказа, смена
  статуса оплаты/доставки через `admin_update_order_status`.
- **Товары**: полноценные формы создания/редактирования с загрузкой
  изображений, управлением размерами и остатками, подтверждением
  изменений через before/after-диф перед сохранением.
- **Категории**: управление категориями.
- **Низкие остатки**: отдельный экран для товаров, близких к исчерпанию.
- **Покупатели**: список, управление ролями и панель с деталями клиента,
  включая историю действий (audit).
- **Отзывы**: очередь модерации отзывов на товары.
- **Финансы**: разбивка выручки и аналитические графики (линейные,
  столбчатые, donut).
- **Журнал аудита**: лента действий администраторов по всей панели.
- **Настройки**: конфигурация методов доставки и оплаты.

Отдельного сценария регистрации админов нет — роль выдаётся один раз, вручную,
своему собственному аккаунту:

```sql
-- один раз через SQL-редактор Supabase или psql "$DATABASE_URL"
update public.profiles p
set role = 'admin'
from auth.users u
where u.id = p.id
  and lower(u.email) = lower('you@example.com');
```

В `profiles` нет колонки email (она есть только в `auth.users`), поэтому
сделать это с клиента невозможно — после выполнения выйдите из аккаунта и
войдите заново, чтобы новая сессия подхватила роль.
